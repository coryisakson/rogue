🎲 Tabletop App — Plan v13 (final design)

Working name: Rogue (open to better ones) · Design complete, ready for review, nothing built yet

The pitch

Rogue is an open-source tabletop-game knowledge platform that turns publishers' and authors' own rules into things players actually use. At its heart is a continuously learning, edition-aware, multilingual knowledge base in which every fact traces back to its source, original language first and publisher and author weighted highest. Two products are built on it first: a one-page setup sheet for every game (printed on the smallest paper it fits, player-count exceptions highlighted, original themed design, never more than one page) and a rules-clarification chat that answers only by quoting and citing sources, or says it does not know. Around them sit community-rated links to 3D-printable organizers, BoardGameGeek data and links (we add value; we do not re-rank games), collection matching, affiliate buy links and a scrubbed public Q&A feed. A small team of specialized AI agents (finding sources, managing the knowledge base, building sheets, answering questions, moderating) does the curation under least-privilege permissions, rights gating and human review, and every AI model and storage provider is pluggable, cloud or local. We do not host rulebooks or 3D files: we link, cite and quote within the copyright allowances of the hosting country, honor opt-outs, and invite publishers to authorize more. It is built EU- and GDPR-first so that anyone, whether a library, a game club or a country community, can run their own instance, and it exposes everything through MCP so agents can use it as easily as people do.

1. Vision in one paragraph

The core artifact is the knowledge base: a continuously evolving, self-improving, edition-aware graph of authoritative game knowledge (original language first, publisher/author weighted highest). Everything else is a product built on top of it.

Open source, built for performance and continuous improvement, with all value flowing to the user community. The first two value propositions are:

  1. Setup one-pagers — a generated, always-one-page view of the knowledge base, with player-count exceptions highlighted.
  2. Game chat — a rules-clarification agent that answers by quoting the knowledge base.

Later products (FAQs, collection matching, buy links, the public feed, MCP, Discord) are further views of the same knowledge, so new value propositions are cheap to add. If the KB is right, the products are right; if a product is wrong, the fix goes into the KB.

2a. Language choice: what AI coding agents do best, and what you can read

Recommendation: TypeScript (strict mode) for almost everything. You said you will not write the code but must be able to read it when something breaks. TypeScript reads close to C#, and AI coding agents are among their strongest in TypeScript and Python.
  • Why TypeScript: one language across Astro, the Hono API, the official MCP SDK, the Discord bot, Better Auth, the pg-boss job queue and Playwright (which the fit solver uses to measure overflow). One language means one set of types shared by the web app, MCP tools and bot, which is exactly the anti-drift rule in §2. Strict types also catch many mistakes AI-written code tends to make, before they reach production.
  • Performance: this system is bounded by the database, the network and model latency, not by CPU. Node handles that load comfortably when we pre-generate sheets (§4), cache answers, serve pages statically or from a CDN where possible, and keep Postgres indexed. We enforce this with performance budgets in CI (§7e).
  • Python, only where it wins: PDF layout, OCR and some evaluation tooling have the richest libraries in Python. If the bake-off or ingestion work shows a TypeScript option isn't good enough, run Python as a separate worker that talks to the rest through the job queue. It is not part of the first build.
  • Why not Rust as the main language: it is excellent for speed and memory safety, but it has a steeper learning curve, slower iteration with AI agents (long compile-fix cycles), and it is the hardest of your options for you to read in an emergency. Our bottlenecks aren't where Rust helps. If profiling later finds a real hot spot (say, the fit solver or bulk hashing), a small Rust or WASM module behind a clear interface is the right place for it. Note that you can still use Rust-based agent runtimes such as ZeroClaw or IronClaw as black-box programs without reading their code (§6a).
  • Why not C#: a fine language you already know, but the libraries we depend on (Astro, MCP and Discord SDKs, agent harnesses) are mostly TypeScript-first, so we would be translating instead of reusing.
  • Readability guardrails: strict mode, no any, small modules, a short ARCHITECTURE.md and a RUNBOOK.md written in plain language, and agents instructed (in AGENTS.md) to comment why, not what.

4. Value prop #1 — the one-pager (a view of the KB)

Rule: never more than one page. Approach:

  1. Structured facts in the KB (extracted from sources with citations, human-reviewable) — not free text. Sections: per_player[], shared[], variants[{players, changes, severity}], notes. Each item has qty, icon, optional image.
  2. Paper ladder, tried smallest to largest: Half-Letter (5.5×8.5in) → A5 (148×210mm) → Letter → A4. Pick by region default (US/CA → Letter family, else A4 family); user can override.
  3. Fit solver: render at each size in a headless browser, measure overflow, try density steps (font 10→8pt, 1→2 column, icon-only mode) before moving up a size. Result cached per game+version+language.
  4. Hard cap: if it won't fit on full page at minimum legible size (≈7.5pt), the editor flags the content as too long — it is trimmed, not spilled to page 2. CI test asserts page count = 1 for every sheet.
  5. Player-count callouts: variant rows get a colored badge ("3 players: remove 2 cards"), and the sheet has a player-count strip at the top. A "pick N players" toggle on-screen shows only relevant lines; print version shows all, highlighted.
  6. Outputs: on-screen, print CSS, PDF, PNG (for Discord embeds). Half-sheets: two-up imposition option on Letter/A4 for cutting.

Who makes the sheets: the Designer agent (human-reviewed)

Themed styling (original design, not copied)

  • The Designer agent reads the game's permitted imagery and description and derives style tokens: a color palette, mood, era/genre, a typeface category from a bundled open-font set, and motif ideas (e.g. "nautical, brass, parchment").
  • It then composes the sheet from original ornaments, icons and patterns (generated or from open icon sets) using those tokens. It does not trace, crop, recolor or embed the publisher's artwork, logos, fonts or card art.
  • Originality check: perceptual-hash and embedding similarity of each sheet asset against the game's known source images; anything too close is rejected and regenerated.
  • Trademarked names and logos appear only as plain-text nominative references ("Setup for <Game>"), with a "not affiliated" footer unless the publisher authorizes more.
  • No publisher approval step: because nothing is copied, themes are not sent to publishers for sign-off. If a publisher asks for a change or a neutral theme, we honor the request and update the site then.
  • Theme must still meet contrast, color-blind-safe, and print-friendly rules (low-ink mode available) and the fit solver's one-page cap.

Pre-generation, not on demand

  • The Designer agent and the fit solver tool work as a batch pipeline: for every game, edition and language with sufficient sourced facts, sheets are pre-generated, validated and cached (PDF, PNG, HTML) before users ask, and regenerated when KB facts or the theme change.
  • Agent loop per sheet: choose content and theme tokens → call fit_solver.render() → read overflow/legibility report → adjust content priority or density → repeat (bounded iterations) → validation → review queue. Anonymous visitors only ever fetch finished files from cache.
  • On-demand request_sheet remains for games without one.

5. The knowledge base: ingestion & graph (the core)

Source authority ranking (highest first) — applied only to sources we are allowed to use

  1. Publisher/author official rulebook, errata, official FAQ (original language)
  2. Publisher/author forum & social posts (BGG designer/publisher-verified accounts, publisher sites)
  3. Official translations (flagged as derived from #1)
  4. Community FAQs / threads (upvoted, rules-lawyer reputation)
  5. User submissions

Source ─has_chunk→ Chunk(text, lang, embedding, page/anchor)
Chunk ─states→ Rule(concept, text) ─clarified_by→ Chunk

Retrieval: original-language chunks are always fetched first; translations are used only for display. Conflicts resolve by authority rank, then recency (errata beats base rules), and the answer states the conflict.

Rights rule (updated in v10): we fetch, cache and quote only within the copyright allowances of the country where the solution is hosted, and we honor every opt-out (robots.txt, machine-readable text-and-data-mining reservations, site terms, publisher requests). We still never republish a full rulebook, serve cached copies to the public, or host rules files. Caches are private working copies for indexing and quoting; the public sees short, attributed excerpts, facts we extracted, and links. Where policy or publisher wishes forbid even that, the source drops to link-only and the "Contact the publisher" flow applies.

Not legal advice: allowances differ a lot by country (US fair use is judged case by case, the EU has a quotation exception plus a text-and-data-mining exception that rightsholders can opt out of, the UK, Japan and others differ again). So the rules live in a configurable Jurisdiction Policy (below), set by the site owner for the hosting country, and open legal questions are tracked in the Review Log (§14) instead of blocking the build.

Rights status is a hard gate in the ingestion pipeline: a source cannot enter the KB without a recorded grant or license, and the grant's scope (index / quote / host / translate / extract facts) is checked again at answer time. Revocation removes the content and its derived chunks and embeddings.

Jurisdiction Policy engine

  • Default profile: EU. Assume hosting in the EU. GDPR is the privacy baseline for every instance, and the copyright profile is the EU one: the text-and-data-mining exception in Article 4 of Directive (EU) 2019/790 (which rightholders can opt out of by machine-readable means), the quotation exception as each member state implements it, and the database right. Where another region is stricter on a specific point, a stricter overlay applies to instances operating there (see §7f); the stricter rule wins.
  • Config, not code: a versioned policy file for the hosting country/region sets, per source type: may fetch? may cache privately (and for how long)? max excerpt length and count? translation for display? must honor robots/TDM opt-out? image handling? Changing hosting country means changing the policy and re-evaluating existing content.
  • Enforced in the KB service (not in prompts): ingestion, quoting, and image display all call the policy check; a decision and the policy version are recorded with every fetch and every quote.
  • Opt-out discovery: robots.txt, meta tags, HTTP headers, TDM-reservation protocols, ToS pages, and publisher portal flags are checked on every fetch and re-checked on re-crawl; an opt-out later removes derived content on the next cycle.
  • Polite fetching: honest user-agent with contact URL, rate limits, caching with conditional requests, no paywall or login circumvention, no scraping where an official API exists.
  • Visitors from other countries: content is served per the hosting policy; a geo-aware takedown contact path is always visible. Users' own countries are logged for later review (§14).
  • Where this overrides a publisher: it doesn't. A publisher grant can widen what we do (e.g. allow longer quotes, hosting a PDF) or narrow it (opt-out), and the narrower of policy and grant wins unless the grant explicitly expands.

"Contact the publisher" flow

  • Game pages without authorized rules show a clear banner: "We don't have publisher-authorized rules for this game. Help us get them."
  • One-click Request authorization (signed-in users): sends a templated, polite email/form to the publisher contact we have on file, explaining what we are and what we ask for (permission to index and quote their rules, optionally a link or file feed). Users can edit the message and add their own note.
  • Public demand counter per game ("37 players asked for this") shown to publishers, plus rate limits so we never spam: one outreach per publisher per period, aggregated across users.
  • Status shown on the page: Not requested → Requested → Publisher responded → Authorized / Declined. A declined publisher is respected and not re-contacted.
  • Also lists the publisher's official site, rules page and support contact so users can reach out directly.

Publisher portal (free)

  • Publisher verifies domain ownership, then claims their games.
  • Chooses a grant scope per game and per file; can supply a URL or push updates, errata and new editions via a feed or webhook, with versions tracked automatically.
  • Can review and correct setup sheets, FAQs and answers about their games, see top unanswered questions, and revoke anytime.
  • Verified publisher or author content gets the top authority rank automatically.

What still fills the gap without rights

  • Community-authored setup facts: counts and layouts are facts. Contributors write them in their own words from their own copy, with page references (no copying of rulebook text, no uploaded rulebook files). Marked community-contributed, not publisher-verified.
  • Metadata and links from sources whose API terms permit it (BGG is subject to approval, §7a), with buy links and publisher contact info.
  • Takedown and correction: a prominent contact path; fast removal on request.

Open points: user-uploaded rulebooks are not allowed in the shared KB. Whether a user may attach their own copy for private, per-account question answering that is never shared is a separate decision (see §13). The same rights-first rule applies to forum posts and third-party sites: use only through terms-compliant APIs or with permission, short attributed excerpts at most, always linked. Logged in the Review Log (§14). I am not a lawyer.

5b. Value prop #2 — how game chat answers (KB-first, quote everything)

  1. Resolve context: game, edition/version (from the question, the user's collection, or ask), player count, expansions, language.
  2. Tier 1 — Authoritative: retrieve from rulebook, errata, official FAQ, and author/publisher sites and posts. Quote the original-language passage verbatim (only from sources whose rights status allows quoting, §5a) with source, publisher/author, edition, page/anchor and date; add a translation beneath if the user's language differs.
  3. Tier 2 — Community: only if Tier 1 does not settle it. Forum posts and other websites, clearly labelled "unofficial", ranked lower, never overriding Tier 1.
  4. No authorized source: if a game has no usable official source, chat says so up front ("No publisher-authorized rules are in our knowledge base for this game"), shows the Contact the publisher call to action, and answers only from attributed community-contributed facts, clearly labelled, or declines. It never reproduces rulebook text it is not licensed to hold.
  5. No source, no claim: if no source supports an answer, chat says "No source in the knowledge base answers this", shows the closest passages with attribution, and offers to queue the question for the Librarian/Scout or publisher outreach. It does not present unsourced rulings. (Changed in v10 to meet the always-attribute rule; see §5e.)
  6. Forum posts and other sites are Tier 2 only when use is terms-compliant, and appear as short attributed excerpts with a link.
  7. Weights are explicit and configurable: official rulebook/errata > publisher/author posts > official translations > verified community rulings > forum posts > other sites. Conflicts are shown, not hidden.

5c. Editions, updates & continuous learning

  • Edition-aware model: every Source and Rule belongs to an Edition (or "all editions") with effective_from, supersedes, and errata_for links. Answers state which edition they apply to and flag differences ("2nd ed. changed this; your copy is 1st ed.").
  • Both versions stay queryable: old rules are never deleted, just marked superseded; the agent answers per edition when it matters.
  • Freshness pipeline: scheduled re-crawl of official sources, content-hash change detection, diff of rules, auto-flag affected FAQs and setup sheets for re-review, notify subscribers.
  • Feedback loop: thumbs up/down, "this contradicts the rulebook" reports, and moderator corrections feed an evaluation set. Corrected answers are re-tested after every change.
  • What "learning" means here: the knowledge base and retrieval improve continuously (new sources, better chunking, re-ranking weights tuned on feedback). We do not train models on user questions by default, which keeps privacy simple and model swaps painless.
  • Regression suite: a growing, public set of question → expected-citation tests runs in CI and on every model/config change, so upgrades cannot silently make answers worse.

5d. Images & artwork

  1. Publisher photos first: official press kits, media pages, and images explicitly offered by the publisher or author (via the publisher portal grant or a feed). Stored with the grant scope and credit text.
  2. Openly licensed images (e.g. CC licenses, public domain) with the license and author recorded and shown.
  3. Curated from other sites where allowed: only if the Jurisdiction Policy and the site's terms/API permit it; otherwise link out or embed through the site's sanctioned embed/oEmbed. Prefer hot-linking or embed over copying when terms allow, and cache only what the policy permits.
  4. User-contributed photos of their own copies, with a license/consent grant from the uploader.
  5. Every image has an image record: source URL, author/publisher, license or grant, date fetched, policy decision, alt text, credit line. No record means it is not shown. Takedown removes the file and all derived thumbnails.
  6. Fallback is a generic themed placeholder, never an unlicensed image.

If it can't be attributed, it isn't shown.

5f. Copyright & trademark for a board-game site: research summary

Research summary, not legal advice. I read search results and the text of the EU Directive, not every article in full. Points marked (verify) come from my general knowledge and are logged in §14.

Copyright: what is and isn't protected

  • Game rules and mechanics as ideas or systems are generally not protected; the way they are expressed is. The exact wording of a rulebook, its layout, artwork, card and flavor text, component designs and logos can be protected. The Copyright Alliance and a 2026 Loughborough University explainer both say copyright covers original expression, not the method of play. The US roots are Baker v. Selden (1879), which held that a system described in a book is not protected by the book's copyright. EU courts similarly ask for an original, sufficiently identifiable expression (e.g. Levola Hengelo, 2018) (verify).
  • Facts and procedures are the safest material: component counts, starting resources, turn order, player-count tables. Extracting them into structured data in our own words and our own layout is the lowest-risk thing the plan does. Close paraphrase or machine translation of whole passages is where it gets risky, because that can be a derivative of the text. (my reasoning; logged R3)
  • Text and data mining in the EU: Article 4 of Directive (EU) 2019/790 lets anyone make reproductions and extractions of lawfully accessible works for text and data mining, unless the rightholder reserved those rights "in an appropriate manner". For content published online, the Directive's recital says that means machine-readable means, including metadata and the website's terms and conditions, and that copies may be kept only as long as necessary for the mining purpose. Article 3 (research) applies to research organizations only, which we are not.
  • Quoting: the EU also has a quotation exception, implemented differently by each member state, that generally needs a legitimate purpose, attribution and a limited amount (verify). This is why the chat quotes short passages with source, edition and page and links out for the rest.
  • Database right: separate from copyright, it can protect against substantial extraction from a database. It matters for catalog and retailer data and for BGG-style sources, not for rulebooks. The Directive's recitals note it alongside text and data mining.
  • Patents on game mechanics are rare but exist (verify); low priority.

Trademark

  • Game titles, publisher names, logos and slogans are protectable as trademarks (the EPGD legal guide gives this as the standard split: names and logos are trademark, wording and art are copyright).
  • Using a name to identify the product is generally allowed as nominative or referential use, if it is needed to identify the goods, done in line with honest practices, and does not suggest affiliation or endorsement. INTA's fact sheet gives EU examples: independent repair shops using the BMW name, and blades marked as compatible with Gillette handles.
  • Where it breaks: using a mark as our own brand, name or domain; logos or styling that look official; implying a partnership; or placing the name in a way that confuses sources. Commercial context (affiliate links next to a mark) is not disqualifying but is a point to review. (logged R5)
  • Accessories: saying an organizer is "for Game X" is the same referential use, which is what INTA's compatibility example covers.

Why this split

  • Least privilege: the agent that reads untrusted web pages (Scout) can't write to the KB; the agent that writes to the KB (Librarian) can't browse; the agent facing users (Concierge) can't change anything. A prompt injection in one stage has nowhere to go.
  • Different skills, different models: cheap fast models for fetching/triage, strong models for extraction and verification, a second model to cross-check sheet numbers and chat citations, small local models for moderation.
  • Pipeline: Scout → (quarantine) → Rights Officer → Librarian → eval gate → KB → Designer → review queue → publish. Each handoff is a queue message with provenance attached.
  • Start with fewer processes: several roles can run as modes of one worker at first (e.g. Scout+Rights, Librarian+Designer) as long as their tool permissions stay separate. Split into separate containers as load or risk grows.

Autonomy ladder (what needs a human)

  • Auto-apply: adding links, metadata, translations for display, re-indexing, dedupe, formatting; changes to community-tier content that pass checks.
  • Auto-apply with eval gate: new facts/FAQs from Authorized or Open license sources, only if the regression suite doesn't drop and citations verify.
  • Human review (moderator or verified publisher): every new or changed setup sheet (at launch), anything that changes a sheet's counts, resolves a rules conflict between sources, rights-status changes, takedowns, outreach to a new publisher, code/config merges.
  • Confidence and diff are shown in the review queue; approvals train the thresholds over time.

How it "continuously learns" (safely)

  • Playbooks as versioned files: what the agents learn (e.g. "this publisher posts errata on page X", "rulebook PDFs for this publisher use two-column layout") is saved as skills/playbooks in a git repo, reviewed via PR like code. Nothing opaque, everything diffable and revertable (same idea as OpenClaw's file-based SKILL.md and Hermes skills).
  • KB is the memory for domain knowledge; agent memory holds only operating notes (per-publisher quirks, failure patterns). No user-identifying data in agent memory.
  • Eval-gated improvement: any prompt, playbook, model or weight change must pass the regression suite before it's promoted; automatic rollback on regression.
  • Outcome signals (thumbs, corrections, moderator edits, unanswered questions) become the Steward's work queue, ordered by demand.

Why not run one general agent as "the site"?

  • Prompt injection: the Scout reads untrusted web pages and forum posts; the Concierge reads untrusted user text. A single agent with shell, secrets and write access that does both is the classic exploitable setup. Splitting roles and removing write/shell from anything internet-facing contains the damage.
  • Cost and latency: a general agent loop is overkill for a cited RAG answer; the Concierge should be a small, cacheable pipeline.
  • Operations: the back-office agents do benefit from a full agent: long-running tasks, scheduling, skills, MCP, multiple chat channels (Discord for moderators), self-improvement.

Backup design: simple by default, strong when you want it

  • Level 1 (default, zero setup): a scheduled job writes a compressed logical dump (pg_dump custom format) of the KB database (no secrets, no personal data, so no encryption needed) to a configured external mount point (/backups) nightly, with rotation (e.g. 7 daily, 4 weekly, 12 monthly). One file per run plus a small manifest (schema version, row counts, checksums, app version). Logical dumps restore across Postgres versions and can be inspected with standard tools.
  • Level 2 (optional, finer recovery): continuous WAL archiving to the same mount (or any configured storage provider) via pgBackRest for point-in-time recovery, for example "restore to 10 minutes before the bad import". Off by default; one config flag turns it on. pgBackRest is the mature standard here (PITR, delta restore, encryption, multiple repositories, current release 2.59.3 per its site).
  • Admin console: a Backups page showing the schedule, last success, size, verification status, a Back up now button, and Download (streamed file), plus upload-to-restore into a scratch environment.
  • Config and secrets: app config lives in git/env; secrets are backed up separately in your password manager or secret store, never inside the data dumps. Anything sensitive follows the separate private-data path below.
  • 3-2-1 guidance: mount point on a different disk, a second copy off-box (cloud bucket, another machine, Olares backup), and one copy not writable by the running system (append-only or pull-based) to survive ransomware or a rogue agent.
  • Public data dumps (KB facts, sheets, listings, ratings aggregates, no personal data) are a separate community export, not the backup.

Provider types

  • Built in: local (any path or mount, including NAS/NFS/SMB mounts), s3 (any S3-compatible service: AWS S3, Cloudflare R2, Backblaze B2, Wasabi, MinIO, Ceph, Garage), gcs, azure-blob, sftp / rclone (rclone alone unlocks 70+ backends, so we do not write each one).
  • Plugin contract: a provider implements put / get / list / delete / stat / signed-URL (where relevant) / optional object-lock. Community can add providers like model providers. The conformance test suite must pass before a provider is "supported."
  • pgBackRest: supports local, S3, GCS and Azure repositories natively and can have several at once, so the WAL/PITR repository follows the same config. (Check its current docs for supported options when we configure it.)
  • Cloud readiness: the first release ships only the container-mount provider, but the interface, config schema and conformance tests are written against AWS S3, Azure Blob Storage and Google Cloud Storage from day one, so adding each is a provider plugin and not a redesign.
  • Per-purpose config with fallbacks and multiple destinations, e.g. backups: [local:/backups, s3:r2://bucket] meaning write both, restore from either.

Making a provider switch painless

  • All stored objects are referenced by logical keys plus a provider alias in the DB, never absolute paths or provider URLs, so moving data does not rewrite records.
  • Built-in migrate command: storage migrate --purpose backups --from local --to s3 copies, verifies checksums, flips the alias, and keeps the old copy until you confirm. Resumable and idempotent.
  • Dual-write mode during migration so nothing is lost mid-switch.
  • Only the private-data class is encrypted (client-side, with keys you hold, separate from provider credentials), so changing or distrusting a provider never exposes it. Public KB data is stored as-is.
  • Credentials come from env/secret store per provider, scoped least-privilege (backup writer cannot delete older backups on the protected copy, Concierge has no storage credentials at all).
  • Health and cost checks: the Operator monitors capacity, errors, egress and latency per provider and flags cloud spend drift.
  • Durability ladder to document for users: single local disk < mirrored disks/NAS < local + off-site cloud copy < multi-region object storage. The admin console shows the current level for each purpose and a plain-language recommendation.

The database engine itself stays Postgres; "pluggable" there means a connection string (self-hosted, managed Postgres, or a cloud provider with pgvector), not a different engine.

Recovery you can trust

  • Automatic restore tests: weekly, the system restores the latest backup into a scratch database, runs migration checks and a smoke subset of the eval suite (counts match the manifest, sample questions still cite the right sources), and reports pass/fail. A backup that hasn't been restored is only a hope.
  • Runbooks as code: restore --to scratch|prod --at <time|backup> in one CLI, documented in the repo, usable by a human or an agent. RTO/RPO targets are written down (suggested starting point: RPO 24h at Level 1, minutes at Level 2; RTO under an hour for a small deployment).
  • Schema migrations are versioned and forward-tested against restored backups; every backup stores its schema version so old backups remain restorable.
  • Rights revocations survive a restore: a small append-only tombstone log (revoked grants, takedowns, deleted accounts) is kept outside the restorable data and replayed after every restore, so restoring an old backup can never resurrect content a publisher withdrew or personal data a user erased.
  • Rebuildable data is rebuilt, not trusted: embeddings, search indexes, rendered sheets and caches are derived; after a restore they can be regenerated from the facts and sources. Backups can skip them to stay small (option to include for fast recovery).
  • Disaster paths covered: bad deploy or migration (restore + roll back), bad agent action (revert from the audit log, then restore to scratch to compare), corrupted disk (restore to new host), lost host (restore from off-box copy), compromised credentials (rotate, restore from the immutable copy).

7c. Community ratings (5-star) on everything except games

  • Rateable objects: accessory/organizer listings, buy links/retailers, FAQs, AI chat answers, setup sheets, community-contributed facts, source links, and publisher outreach responses where relevant. Games are not rateable: BGG owns game rankings and we do not duplicate them.
  • One generic rating system in the core API: rating(target_type, target_id, user_id, stars 1–5, optional note, created_at). Signed-in users only; one rating per user per object, editable. Anonymous users see aggregates but cannot rate.
  • Display: average, count, distribution, and a "Wilson-style" confidence-adjusted sort so one 5-star vote doesn't beat 200 4.6s. Show "N ratings" always; hide the average below a minimum count.
  • Anti-abuse: rate limits, account-age and activity weighting, duplicate and brigade detection, creators/publishers cannot rate their own items, moderator tools to void ratings; ratings are not purchasable.
  • Feedback loop into the KB: low-rated AI answers go to the Librarian for review; consistently high-rated answers become FAQ candidates; poorly rated sheets get re-verified; low-rated links are re-checked or dropped. Ratings are a training signal for the evals, never a source of rules truth (a popular wrong answer is still wrong; rules come from sources, §5b).
  • Contextual ratings: rating an AI answer also asks (optionally) why in one tap: "wrong rule", "wrong edition", "unclear", "missing citation", "helpful".
  • Privacy: public shows aggregates and (optionally) display name on reviews; the anonymous feed shows aggregate stars only, no identity. MCP: rate_item (auth), get_ratings (anon).

7d. BGG as the ranking authority; our added value

  • Show on every game page (when permitted and available): BGG title, year, designer, publisher, player count/best-at, play time, weight, short descriptor, and a prominent "View on BoardGameGeek" link. Rankings and BGG ratings are shown as BGG's, attributed and linked, never recomputed or competed with.
  • Our line: we are not a database, ranking, review or forum site. We add what BGG doesn't offer: one-page setup sheets, KB-cited rules chat, edition-aware clarifications, organizers, and agent-friendly access (MCP).
  • BGG attribution/branding requirements and caching rules must be followed; fetching goes through the BGG adapter with rate limits and the approved API token. If BGG access is denied or removed, game pages still work from publisher/user metadata, just without the BGG panel.
  • Game identity key = BGG id when available, so collections, editions and external links line up.

7e. Open source & performance principles

  • License (decision needed): AGPL-3.0 keeps hosted forks open and protects the community; MIT/Apache maximizes adoption. I lean AGPL for code and CC BY-SA (or CC0 for pure facts like counts) for community-authored sheet/FAQ data. Publisher-owned content keeps its own rights and is only linked/quoted.
  • Public data dumps and a public API so nobody is locked in; fully self-hostable with one docker compose up and local models only.
  • Contribution paths: add games, fix sheets, translate UI, add ingestion adapters, add model providers. CONTRIBUTING, good-first-issues, public roadmap.
  • Performance budgets enforced in CI: sheets and game pages statically cached and CDN-served (target LCP < 1.5s on mid-range mobile, JS < 100KB on read-only pages); Postgres index and query-plan tests; LLM answers cached by (question, edition, source-version).
  • Telemetry opt-in only, self-hosted analytics, no ad trackers.
  • Affiliate links are the funding model but never alter ranking or answers; disclosed on every page and removable in self-hosted copies.

7f. Many instances: hosting your own (library, game club, country)

Design goal: anyone can run their own instance from one container deployment and one config file. Our hub is just the biggest instance.
  • Instance profile (one file): hosting region, Jurisdiction Policy pack, privacy profile, languages, AI model providers (including local-only), storage providers, branding and theme, feature flags (public feed on or off, chat open to sign-ins only), and affiliate programs per country. An init wizard creates it with safe defaults.
  • Policy packs: eu is the default. Others (us, uk, jp, and so on) are added as the community contributes and reviews them. Each pack bundles the copyright allowances (§5a) and the privacy rules for that region.
  • Privacy: EU/GDPR is the baseline everywhere, and it is widely regarded as the strictest overall regime. Some Asian laws are stricter on particular points: China's PIPL has no "legitimate interest" basis, requires security assessments for sending personal data abroad and localization above thresholds, and has fines up to 5% of revenue; South Korea's PIPA was amended in 2023 to restrict processing abroad. So: stricter overlays (cn-pipl, kr-pipa) ship as policy packs that an instance operating or targeting those countries must enable, and the stricter rule wins. We do not target those countries from the EU hub; PIPL also has extraterritorial reach, which is logged in §14.
  • Each instance is its own data controller. Instances never send user data upstream. Personal data stays in each instance's private database (§6b).
  • Modes: (1) public community instance; (2) library or club instance, public or private, with local-only models and a local overlay for house rules, owned-game lists and local notes that are never pushed upstream; (3) air-gapped local-only deployment.
  • Sharing knowledge: instances can pull the hub's public data dump (facts, citations and locators, sheets, listings, aggregated ratings; CC BY-SA or CC0 as chosen in §7e) and contribute improvements back as proposals into the review queue. Cached source text, excerpts and anything fetched under one country's allowances are not synced, because a quote that is lawful in one jurisdiction may not be in another. Each instance re-derives excerpts under its own policy. (logged R15)
  • Operations stay simple: the same backup design (§6b) and storage plug-ins apply to every instance, with a container mount by default.

Owner access: a minimal admin console, an ops CLI, and the repo

  • Admin Console (small, web): sign in with the same social login plus a passkey, owner role. Pages for backups (status, back up now, download, restore into scratch), the review queue, Jurisdiction Policy and instance profile, model and storage providers, feature flags and the Review Log. It does nothing the ops CLI cannot do.
  • Ops CLI: one local command (rogue backup|verify|restore|health|storage migrate|policy ...) that works even when the web app is down. The Operator agent calls the same commands through a scoped wrapper (§6b). This is also the break-glass path.
  • Roles: Owner, Moderator, Publisher (scoped to their games), Operator agent (scoped, approval-gated). Destructive actions (production restore, purge, policy change) need a second confirmation.

  • Deferred: a remote Admin MCP is intentionally out of the plan for now. If you want agent-driven administration later, it would be a new, separately secured endpoint.

9. Auth, privacy, the public feed

  • Sign-in screen = provider buttons only (Google, Apple, Discord, GitHub, Microsoft). Store minimum: provider id, display name, avatar, language.
  • Public feed shows question + answer + game + citation only — no user identity. Pipeline: PII scrub → NSFW/abuse classifier → hold if uncertain → publish. Users can opt out per question. Admin/moderator removal tool.
  • New-game submissions go to a "pending" state with automated checks (duplicate detection, source verification) before going public.
  • Abuse controls: per-user chat quotas, bot detection on anonymous search, prompt-injection hardening for ingested text (treat sources as untrusted data).

Privacy & regulatory compliance (GDPR and similar)

  • Data minimization: store provider ID, display name, avatar, language, chosen collection data, and activity needed for the product. No tracking cookies; privacy-friendly self-hosted analytics, opt-in only.
  • Lawful basis recorded per purpose (contract for the account, consent for optional features like public profile or BGG import, legitimate interest for security/abuse logs), with a plain-language privacy notice and records of processing.
  • User rights built in: self-service export (machine-readable), correction, deletion/erasure, restriction, objection; also runnable through the ops CLI so the Operator can prepare them for human sign-off. Deadlines tracked (e.g. one month under GDPR).
  • Chat and feed data: questions can contain personal data; they are PII-scrubbed before any public display, have a retention limit, and are unlinkable from identity in the public feed. Users can delete their history. No training of models on user data by default.
  • LLM and other processors: data-processing agreements with any cloud provider; a "local models only" and "EU region only" mode per role (§6); no personal data sent to providers that don't need it; prompts exclude identity.
  • Backups and erasure: erased accounts are recorded in the tombstone log (§6b) and re-applied after restores; backup retention is bounded and documented so deleted data ages out.
  • Children: minimum age policy and no features aimed at under-13/16 without parental consent flows (varies by country; logged in §14).
  • Breach readiness: detection, audit log, incident runbook, and notification templates (72-hour GDPR window).
  • Contributors of content: clear licensing terms when users submit facts, photos, or links (grant to us, attribution, removal rights).
  • Also consider: cookie/ePrivacy rules, accessibility law (e.g. European Accessibility Act, WCAG AA), consumer rules for affiliate disclosure (FTC and EU equivalents), DSA notice-and-action for hosted user content, and the data-protection rules of the host country. These are tracked in the Review Log (§14); no formal legal review is planned yet.

12. Key risks

  • Allowance-based fetching/caching is legally nuanced and varies by hosting country; fair-use-style judgments are not automatable. Mitigate with the Jurisdiction Policy, conservative defaults, opt-out honoring, short excerpts only, no public caches, a Review Log of open legal questions (§14), and fast takedown. No formal legal review is planned yet, which is an accepted risk. This is a deliberate step up from v4's "no fetching without a grant".
  • Sheet styling resembling publisher art — mitigate with style tokens instead of assets, similarity checks, and honoring any publisher request when one arrives.
  • Immature harnesses — DeepSeek Harness is a v0.1 preview and the "claw" family is months old; mitigate with the harness-agnostic spec/adapter design and a scored bake-off.
  • Multi-agent complexity — coordination bugs and cost; mitigate with queue-based handoffs, role budgets, replayable event logs, and starting with merged workers.
  • GDPR/DSA/accessibility obligations — require early design (erasure vs. backups, processors, retention); mitigate with the compliance tooling in Phase 5c and the Review Log (§14).
  • Attribution gaps — a claim without a source slipping through; mitigate with schema constraints, claim-level verifier, and API errors on unsourced results.
  • Provider lock-in / migration pain — logical keys, a single interface, dual-write migration, and conformance tests keep storage swappable. Single local disk is the weakest durability tier; the admin console says so plainly until a second copy exists.
  • Data loss / unrestorable backups — mitigated by automatic restore tests, off-box and immutable copies, versioned schemas, runbooks, and a break-glass CLI (§6b).
  • Restore resurrects withdrawn content — tombstone log replayed after every restore.
  • Admin agent blast radius — scoped admin tools, human approval for destructive actions, protected backup copy it cannot touch.
  • Single-database coupling — one engine simplifies ops but means a Postgres problem hits everything; mitigated by Level 2 PITR and documented rebuild path.
  • 3D-print site terms / link rot — each site's API and indexing terms vary; use per-site adapters with a rights status, submit-only where needed, and scheduled link-health checks. Linking is generally low-risk, hot-linking images and copying descriptions is not, so keep stored data minimal. Licenses are shown but not enforced by us.
  • Rating manipulation — fake or retaliatory ratings from creators, publishers or brigades; mitigated by §7c controls. Ratings never override sourced rules.
  • BGG dependency — API token, terms, rate limits, and attribution rules; adapter isolation plus graceful degradation.
  • Wrong numbers on a sheet — the most visible failure. Mitigate with cited facts only, second-pass verification, gold-set evals, human approval at launch, and an always-visible error report that routes straight to the Librarian.
  • Agent security — prompt injection via ingested pages or user chat; mitigated by role separation, no shell/writes on the public agent, KB-enforced rights gate, sandbox + egress allowlist, review queue (§6a).
  • Runaway cost/behavior — per-role budgets, rate limits, kill switch, audit log.
  • Over-trusting self-improvement — learned playbooks only promote through evals and PR review.
  • KB quality is the product — bad extraction poisons sheets and chat. Mitigate with provenance everywhere, review tooling, and the eval suite from Phase 2 (before any product ships).
  • Content rights — reduced by the rights-first rule (§5a), but still the top risk. Residual risks: coverage (many games will start with no authorized source), publisher non-response, and community-contributed facts drifting too close to copied text. Mitigate with scope checks, similarity detection on submissions, and fast takedown.
  • Cold start — with no scraping, early catalog depth depends on open-license games and friendly publishers. Plan: start with open-license/indie/crowdfunded publishers, show demand data to larger ones.
  • Rules-answer accuracy — wrong rulings hurt trust; mitigate with citations, confidence, "not covered", and an eval suite.
  • Fit solver complexity — decouple from content early; prototype in Phase 1.
  • Amazon Associates — accounts are per country, require qualifying sales, and Amazon's product API requirements change; budget time to verify current terms.
  • BGG terms / API access — see §7a; keep behind an adapter.
  • Edition ambiguity — users often do not know their edition; the agent must ask or show both rather than guess.
  • Local model quality — small models cite worse; the eval suite sets a minimum bar per role.
  • LLM cost — quotas and caching of repeated questions.
